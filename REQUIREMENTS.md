# Cilium TIME_WAIT / SNAT Port Reuse — Reproduction Requirements

## Goal

Reproduce the race condition where:
1. Client pod simultaneous-closes with target server → both enter TIME_WAIT
2. Client pod dies → Cilium scrubs its CT entries, freeing the SNAT port immediately
3. A new client pod starts and is assigned the same SNAT port
4. Target server (still in TIME_WAIT) responds to new pod's SYN with RST → connection rejected

## Terminology

- **Target server**: long-running TCP server the client pods connect to, outside the cluster
- **Orchestration pod**: k8s Deployment that uses the k8s API to spawn client Jobs at a
  target rate with randomised inter-arrival jitter
- **Client jobs**: short-lived `batch/v1` Jobs created by the orchestration pod; each opens
  N connections to the target server, completes the protocol, then exits 0

## Topology

```
[target server host]               [k8s cluster node]
┌────────────────────┐             ┌──────────────────────────────────┐
│  Docker            │             │  Cilium SNAT                     │
│  target-server     │◄────────────│  client job pods (nodeSelector)  │
│  :9000             │  TCP/SNAT   │  orchestration pod (same node)   │
│  SQLite → /data    │             └──────────────────────────────────┘
└────────────────────┘
```

Client pods are pinned to a cordoned node via `nodeSelector`. Their traffic to the target
server's external IP exits the node and is SNATed by Cilium — this is the path that
triggers the bug. The node must be cordoned so the ephemeral port pool available for SNAT
is shared only among our pods, increasing collision probability.

## Environment

- **Cluster**: any Kubernetes cluster running Cilium
- **Namespace**: `cilium-repro`
- **Target server host**: any host reachable from the cluster node via a routable IP
- **Client/orchestration node**: a cordoned node (`kubectl cordon <node>`)

## Components

### 1. Target Server (`target-server/server.py`) — Docker on external host

- Long-running Python TCP server, one thread per accepted connection
- `net.ipv4.tcp_fin_timeout` left at kernel default (60 s); container-scoped
- On receiving `"CLOSE"` from client: calls `shutdown(SHUT_WR)` and drains (simultaneous close)
- SQLite DB at `/data/cilium_repro.db` (bind-mount a host directory)
- Background thread polls `/proc/net/tcp` every 2 s to detect TIME_WAIT entries by src_port,
  updating `time_wait_at` and `released_at` in the DB

#### Protocol (per connection):

```
Client → Server:  "HELLO SERVER 👋\n"
Server → Client:  "HELLO CLIENT 🎉\n"
Client → Server:  "HOW ARE YOU? 🔄\n"
Server → Client:  "DOING GREAT! ✅\n"
Client → Server:  "CLOSE\n"           ← client calls shutdown(SHUT_WR) immediately after send
Server:  receives "CLOSE" → calls shutdown(SHUT_WR) immediately (simultaneous FIN)
Both sides drain then close()
```

The simultaneous `SHUT_WR` on both sides causes both endpoints to enter TIME_WAIT. The
server-side TIME_WAIT is what matters: if Cilium frees the SNAT port while the server is
still in TIME_WAIT, the next new connection on the same port receives a RST.

#### SQLite schema:

```sql
CREATE TABLE connections (
    id           INTEGER PRIMARY KEY,
    src_ip       TEXT,
    src_port     INTEGER,
    accepted_at  REAL,      -- unix timestamp: ACCEPT event
    time_wait_at REAL,      -- unix timestamp: first seen TIME_WAIT in /proc/net/tcp poll
    released_at  REAL,      -- unix timestamp: TIME_WAIT gone, port free
    is_active    INTEGER DEFAULT 1   -- 0 = closed; row is never deleted
);

CREATE TABLE ss_snapshots (
    id            INTEGER PRIMARY KEY,
    snapshot_time REAL,
    raw_output    TEXT
);
```

### 2. Orchestration Pod (`orchestration/main.py`) — k8s Deployment on cordoned node

- Python pod using the `kubernetes` client library
- Creates `batch/v1` Jobs at a target rate using Poisson inter-arrival times:
  `sleep(random.expovariate(RATE_PER_SECOND))` between each Job creation
- Default rate: **20 pods/minute** (configurable via `TARGET_RATE_PER_MIN` env var)
- `ttlSecondsAfterFinished: 120` — k8s automatically cleans up finished Jobs
- `nodeSelector: kubernetes.io/hostname: <cordoned-node>` + toleration for
  `node.kubernetes.io/unschedulable:NoSchedule`

### 3. Client Job (`client/client.py`) — `batch/v1` Job (generated by orchestration pod)

- Opens `NUM_CONNECTIONS` TCP connections simultaneously (default: 10)
- All connections complete the protocol, then wait on a `threading.Barrier` before closing
- The barrier ensures all `shutdown(SHUT_WR)` calls fire at roughly the same instant,
  freeing the maximum number of SNAT ports in a single burst
- `NUM_CONNECTIONS` connections freed at once simulates a connection pool shutdown on pod death
- `nodeSelector` and tolerations same as orchestration pod

### 4. UI (`ui/app.py`) — Flask dashboard

- Dark-themed dashboard, auto-refreshes every 5 s
- Stats banner: total connections, TIME_WAIT events recorded, port reuse candidates, bug hits
- Port reuse events table: `src_port`, `time_wait_at`, `accepted_at` of new connection, gap
- **Bug hit**: gap < 60 s (server TIME_WAIT window) — highlighted red
- Collapsible port reuse section, auto-expands when bug hits present

### 5. Manifests (`k8s/`)

- `namespace.yaml` — `cilium-repro` namespace
- `rbac.yaml` — ServiceAccount + Role (create/list/watch/delete Jobs) + RoleBinding
- `orchestration-deployment.yaml` — orchestration pod Deployment (fill in placeholders before apply)
- Client Job YAML generated programmatically by orchestration pod (not a static manifest)

## Why This Triggers the Bug

Cilium's `scrubIPsInConntrackTableLocked()` is called when a pod's IP is removed. It
iterates the conntrack table and deletes **all entries for that pod**, including entries in
`TIME_WAIT` state. From the kernel's perspective those ports are not yet free — the remote
server still has a TIME_WAIT entry referencing them. Cilium then returns those ports to the
SNAT pool, and a subsequent pod that draws the same port immediately gets a RST from the
server when it sends its first SYN-ACK.

The effect is more likely to be observed when:
- Many connections close simultaneously (connection pool shutdown on pod death)
- The SNAT port pool is small (cordoned node → fewer pods → fewer ports in use → higher
  reuse probability)
- `tcp_fin_timeout` is long (default 60 s gives a wide window)

## Resolved Design Decisions

- [x] Simultaneous close: client sends `"CLOSE\n"` + `shutdown(SHUT_WR)`; server mirrors
      immediately — both enter TIME_WAIT (not CLOSE_WAIT/FIN_WAIT)
- [x] Multi-connection per pod with `threading.Barrier` to maximise simultaneous port release
- [x] Rate: 20 pods/min Poisson-distributed (exponential inter-arrival, mean = 3 s)
- [x] SQLite DB on target server host; bind-mounted into Docker container
- [x] Client jobs pinned to the same cordoned node as the orchestration pod
- [x] No shell scripts — orchestration handled by k8s-API-aware Python pod
- [x] Port reuse detection query guards `b.accepted_at > a.time_wait_at` to exclude
      negative-gap artifacts from rows that never entered TIME_WAIT
